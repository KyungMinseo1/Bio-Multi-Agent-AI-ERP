# BioFlow ERP v3.0 — 통합 구매·생산 업무 프로토타입

기존 React + TypeScript + Vite 프로젝트와 IL-7 계산 엔진을 보존하고, 팀원의 FastAPI 기반 다중 에이전트 검토·Orchestrator·서버 DB 발주 흐름을 연결했습니다. 기본 진입점은 구매요청 업무함입니다. 기존 분석 Workspace와 FGF-2 데모는 **기준·시연 설정 → 이전 분석 화면**에서 사용할 수 있습니다. 통합 비교와 이관 범위는 [`docs-team/INTEGRATION.md`](docs-team/INTEGRATION.md)에 정리했습니다.

## 실행

검증 환경: Node 24.13 / npm 11.6, Python 3.14. Node 22.12 이상 권장.

```sh
npm ci
npm test
npm run build
npm run start:local
```

`start:local`은 `.venv`에 설치된 백엔드 의존성과 Alembic DB 마이그레이션이 필요하며, API·작업자·빌드된 웹 앱을 같은 포트로 실행합니다. `npm run start:local` 전에 아래처럼 환경을 한 번 구성합니다.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
cp .env.example .env
npm run build
npm run start:local
```

`.env`의 초기 승인자 이메일·비밀번호 및 세션 비밀키를 설정하면 조직 계정 로그인을 쓸 수 있습니다. API 키는 선택 사항이며 서버 환경변수로만 지정합니다. 키 없이 기본 구매요청·독립 규칙 기반 분석·가상 발주 시연은 작동합니다. 통합 서버의 **실제 AI 검토**는 공급자 키와 모델 설정이 있을 때만 외부 LLM을 호출하며, 설정이 없으면 모의 결과를 생성하지 않고 검토를 막습니다. 브라우저에서 **통합 서버 · 실제 AI → 로컬 시연 계정으로 연결**을 선택하면 로컬 전용 계정으로 DB 저장·읽기·발주 등록을 확인할 수 있습니다. 이 계정은 외부에서 쓸 수 없고, 로컬 시작 스크립트가 비밀값을 `.runtime/local-demo.env`에 제한된 파일 권한으로 생성합니다.

브라우저에서 http://127.0.0.1:4173/ 를 엽니다. 개발용 Vite 서버는 `npm run dev -- --port 5173`으로 실행할 수 있습니다. API 테스트는 `npm run test:api`로 실행합니다. 빠른 정적 웹 미리보기만 필요하면 `npm run preview -- --port 4173`을 사용하되, 서버 저장·실제 AI 기능은 사용할 수 없습니다.

## 공급업체 견적 메일 발송 (선택 기능)

구매요청의 **공급업체 요청·회신** 탭에서 1차 승인과 공급 확인 요청 생성 후 **실제 견적 메일 작성**을 선택합니다. 보내는 사람·받는 사람 주소, 업체, 제목, ERP 생산 일정에서 만든 본문을 수정하고, 견적 회신용 CSV 첨부 및 외부 발송 확인란을 확인해야 실제 발송을 요청할 수 있습니다. SMTP 발송은 승인자 로그인 세션을 요구하며, 발신 주소는 서버의 허용 목록과 일치해야 합니다. 발송 이력은 서버 DB와 감사 로그에 남고 메일 본문·비밀번호는 저장하지 않습니다. 재전송은 새로운 이메일이므로 발송 이력에서 먼저 확인하세요.

메일을 사용하려면 프로젝트 루트 `.env`에 SMTP 자격증명을 서버 전용으로 설정하고 API 프로세스를 재시작합니다. 메일 관리자에게 발급받은 SMTP 호스트·포트·TLS 방식·로그인 이름·앱 전용 자격증명을 입력합니다. `BIOFLOW_SMTP_DEFAULT_FROM`과 `BIOFLOW_SMTP_ALLOWED_FROM`에는 해당 자격증명으로 발송 권한이 있는 주소를 넣습니다. 일반 계정 로그인 비밀번호 대신 메일 사업자의 SMTP용 앱 비밀번호/토큰을 사용하세요. `.env`와 앱 비밀번호를 브라우저 코드나 저장소에 넣지 마세요.

이 기능은 Codex 세션의 메일 MCP를 웹 브라우저에 노출하지 않습니다. 웹앱 서버가 설정된 SMTP 계정으로 실제 메일을 전달하는 방식입니다. 업체 답장은 자동 동기화되지 않으며, 실제 발송 업체는 가상 회신 생성에서 제외됩니다. SMTP 설정이 없으면 작성·미리보기는 가능하지만 발송은 차단됩니다.

## 3–5분 시연 순서

1. 최초 재고 위험 팝업에서 **장부6 / 생산 가용2 / 생산 부족10 / 안전 포함 확보 목표12**를 확인합니다.
2. **공급업체 확인 승인 검토 → 공급업체 확인 승인**. 이 1차 승인은 업체 문의만 허용합니다.
3. **공급 확인 요청 생성 → 가상 회신 수신**. B 회신 상세의 확약12개와 3회 납품을 확인하고 Drawer를 닫습니다. A/B는 공급 확인, C는 조건 불확실입니다.
4. **독립 분석 시작**. 네 부서가 동일 ERP·회신 스냅샷을 독립 계산합니다. 단순 조회는 빠르게, 총비용·통합 검증은 더 길게 표시합니다. 각 판단 행을 눌러 실제 참조 행·수식·결과·구조화 JSON을 확인합니다.
5. Orchestrator의 **추가 검증 실행**. A 단가 우위와 재고/총비용 제약 충돌을 해당 부서만 다시 검토합니다. `남은 분석 모두 실행`으로도 같은 함수를 실행할 수 있습니다.
6. **최종 추천·승인 → 최종 발주 승인 검토 → 최종 승인·발주서 생성**. B12개, 구매·운송1,230만원, 총비용1,275만8,800원을 검증합니다. 내부 PO와 인쇄용 구매발주서가 생성됩니다.
7. **입고 추적 열기**. 기본 선택된 B2회차에 **QC 시작3일 지연**을 적용합니다. 사용 가능11.12, PROD-02 11.11 부족2개 경고와 **AI 재분석·대안 검토**를 확인합니다.
8. 정상 입고 시연은 초기화 후 다시 PO를 생성하고 회차마다 **출하 → 입고 → QC 검사 → QC 적합 → QA 승인 기록(가상 담당자)**을 수행합니다. 마지막에 **생산 투입 반영**을 누르면 3개 생산의 IL-7 총12개가 한 번씩 차감되고 가용2개가 남습니다.

**기준·시연 설정 → 전체 업무 시연 초기화**로 반복합니다. 품질 사용 승인과 구매 승인은 별개의 상태입니다.

## 실제 계산과 승인 경계

- **재고**: 품질·유효일로 Lot를 제외하고 날짜별 생산 수요를 한 번씩 할당합니다. 기존 PO의 확약 입고는 미래 예측에만 포함하며 현재 재고와 중복 가산하지 않습니다. 생산 부족과 안전재고 보충 목표를 구분합니다.
- **회신**: 요청·미회신·조건 불확실·공급 확인·공급 불가·제외 상태, 회신 원문, 회신기한·최종 대응기한·견적 유효기간·최대3회 재문의를 관리합니다. 미확약 수량은 확정 공급에서 제외합니다.
- **독립 분석**: 재고·생산계획, 구매, 품질, 재무의 결과는 같은 원본 버전을 참조합니다. 부서별 선호·제약·대안·미확인 항목·테이블 ID·계산식을 구조화합니다. Orchestrator는 배분·회수·추가 검토·최종 검증을 수행하며 부서 간 직접 토론은 없습니다.
- **일괄/분할/부분**: MOQ·주문배수·입고 확약량을 검증합니다. B8개 부분 회신은 주문 후보8개·구매운송820만원으로 비교하고 전체12개 충족으로 간주하지 않습니다. B8+A MOQ20 조합도 재고·총비용·같은 날 지급 현금을 재계산하여 예산 초과 및 A단독 대비 중복 구매를 표시합니다. 업체별 추가 확약 없이 조합 PO를 자동 생성하지 않습니다.
- **비용**: 구매+운송 소계와 시험+보관+폐기처리를 포함한 총비용을 분리합니다. 구매비에 포함된 폐기 재고 장부가액을 다시 더하지 않습니다. 같은 지급일은 현금 한도를 합산 검증합니다.
- **최종 승인**: 원본/회신 fingerprint·revision·견적 유효기간·1차 승인·확정 공급안·기존 PO를 생성 순간 다시 확인합니다. 동일 구매요청의 중복 발주는 차단합니다. PO는 승인 당시 제품·단가·금액·일정·전략·승인 근거의 스냅샷입니다.
- **후속 추적**: 입고 시 미승인 Lot가 생성되고 QC 적합 이후에도 QA 승인 전에는 사용 불가입니다. QA 서명은 명시적인 가상 담당자 버튼으로 기록합니다. 해당 투입일보다 늦게 승인된 Lot를 과거 생산에 소급 투입하지 않습니다. 지연·온도 이탈은 해당 회차에만 적용하고 기존 PO를 자동 취소하지 않습니다.
- **변경**: 단가·MOQ·재고·생산일·입고일·QC 지연을 편집하면 revision과 변경 이력이 갱신됩니다. 견적 변경은 기존 회신을 무효화하고 재확약을 요구합니다. 수요 변경은 1차 승인 범위도 재검증합니다. 발주 후에는 등록 PO 스냅샷을 보존하며 후속 영향 재분석으로 연결합니다.

고객 납기와 역산 기간(생산5일+완제품확인1일+포장1일+운송1일), 추가 비용 단가, 현금 한도, 승인/확약 문서번호, IL-15 수량, 업체명·담당자는 **추가 합성 데이터**입니다. 실제 제품 함량·보관 온도·활성 변환을 주장하지 않습니다. 고객 납기는 현재 생산일+8일로 설정하며 변경 시 역산 적합성을 검증합니다. 달력일 기준이며 영업일·공휴일 계산은 포함하지 않습니다.

## 저장·구조·검증

기본 시연 상태는 브라우저 localStorage `bioflow-workflow-21`에 보존합니다. 통합 서버 탭에서 **현재 업무 서버에 저장**하면 같은 BioFlow 업무 원본·회신·PO를 API의 서버 DB에도 보존합니다. 로컬 서버의 기본 DB와 세션 설정은 무시 규칙이 적용된 `.runtime/`에 생성합니다. 이전 ERP 원본을 초기 데이터로 재사용하되 이전 승인을 새 2단계 승인으로 전환하지 않습니다. 승인/문의/분석 스냅샷/PO/업무 이력을 보존하며 시연 저장량은 최근 보고서12개·로그400개·알림100개로 제한합니다. 초기화 전 필요한 표는 내보내세요.

- `src/workflow/engine.ts`: 순수 업무 상태 전이와 결정론적 분석
- `src/workflow/FlowApp.tsx`, `workflow.css`: 기본 업무 UI·승인 모달·상세 Drawer·인쇄 PO
- `src/workflow/store.ts`: v2.1 상태 저장
- `src/erp/calculator.ts`, `model.ts`, `DataGrid.tsx`: 기존 계산·관계 데이터·스프레드시트 재사용
- `src/erp/ErpApp.tsx`, 기존 App 내부 LegacyApp: 이전 분석/FGF-2 화면 보존
- `src/workflow/engine.test.ts` 외 기존4개 테스트 파일: 총68개 통과
- `QA-v2.1.md`: 검증 내역

## 실행 모드와 범위

화면의 **규칙 기반 시연 · API 키 불필요** 모드는 로컬 결정론적 업무 분석과 가상 승인·발주 흐름입니다. **통합 서버 · 실제 AI** 모드는 DB 저장, 서버 버전 검증, 병렬 역할 검토, Orchestrator 종합, 담당자 최종 발주 승인·내부 ERP 등록을 제공합니다. AI 검토는 설정된 실제 LLM 제공자를 사용하며, 무자격증명·호출 실패 시 가짜 AI 의견을 대체 출력하지 않습니다. 기본 시연은 공급업체에 연락하지 않고 구매·결제를 하지 않습니다. 위에서 SMTP를 별도 설정하고 승인자가 메일 화면에서 확인한 경우에만 실제 견적 요청 메일을 발송합니다. 메일 발송은 구매 승인·주문 수락·결제와 별개이며, 재고 품질 사용승인은 구매 승인과 분리합니다. 외부 공급망 위험 실시간 수집과 운영환경용 동시성·장기 감사 보존·상시 가용성은 범위에 포함하지 않습니다.

이전 기능·계산 가정의 상세 설명은 `README-analysis-v3.md`에 남겨두었습니다.
